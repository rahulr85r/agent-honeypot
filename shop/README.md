# Pico Mobile — agent-detection storefront

A convincing (fictional-brand) e-commerce site that detects whether the shopper is a
human or an AI agent, across the whole journey: browse → product → cart → sign-in →
checkout. It is the e-commerce sibling of the `case-bank` demo, but the detector here is
built for **real** detection, not demonstration — precision-first, multi-domain, and
honest about its limits.

Nothing here is deceptive in the wild: the brand is invented, there is **no card entry**
(accounts carry store credit), no real orders are fulfilled, and no IP/WebRTC addresses
are collected. You drive your own agents, signed in with your own test profiles.

## Layout: readable `src/`, obfuscated `public/`

You edit `src/`; a build step emits de-telled, obfuscated files to `public/`, which the server
serves. This is what keeps the detection invisible to a visiting agent:

- `src/js/{collector,honeypots,shop-ui,bundle}.js` — readable client sources.
- `src/html/*.html`, `src/store.css` — readable markup/styles (with `data-hp="…"` hooks, design comments).
- `build.js` → `public/` — renames the public API globals to bland tokens (`Collector`→`_px`,
  `PicoHP`→`_ph`, …), recodes the honeypot DOM hooks (`data-hp="decoy"`→`data-k="p"`, …), concatenates
  the four libs into **one obfuscated** bundle at `/assets/app.js` (javascript-obfuscator: string-array
  + base64, control-flow flattening, mangled identifiers), strips all HTML/CSS/JS comments, and collapses
  the four `<script>` tags into one. An agent inspecting the page sees `app.js`, `data-k="…"` attributes,
  and no "honeypot/collector/decoy/webdriver-check" strings.
- **The runtime server stays zero-dependency**; `javascript-obfuscator` is a build-only devDependency.
  (`npm audit` flags a few build-time advisories in its deps — they never ship.)

## Run

```bash
cd shop
npm install          # once — pulls the build-only obfuscator (runtime server itself needs nothing)
npm run build        # src/ → public/  (re-run after any edit to src/)
node server.js       # Node >= 22.5 (built-in node:sqlite)
# → http://localhost:4600           store
# → http://localhost:4600/results?k=<token>   detection log (admin view; token is
#   generated on first start into ./admin.token — without it the log 404s)
PICO_DEBUG=1 node server.js          # also returns the verdict inline in API responses
```

Delete `data/store.db` to re-seed fresh accounts/credit/products. **Edit `src/`, never `public/`**
(public is regenerated by the build and your changes there will be overwritten).

## How detection works (4 domains, fused server-side)

The browser only **collects**; it ships an obfuscated bundle with sensitive actions. All
thresholds and the verdict live server-side (`server/detector.js`), so a visiting agent
can't read how it's judged. Four domains:

- **STATIC** (`collector.js`) — browser fingerprint: UA/UA-CH, platform, plugins, screen,
  canvas hash, **WebGL vendor/renderer** (software GPU = VM/headless), WebGPU, audio hash,
  **font enumeration**, `webdriver` + whether its getter is non-native (stealth tell).
- **ENV** — timezone/locale coherence, the **notification/permission contradiction**,
  media-device and battery presence, speech voices, connection, and an **automation/stealth
  scan** (webdriver, `cdc_`, Playwright/Puppeteer/Selenium globals, and patched native fns).
- **BEHAVIOUR** — live kinematics: mouse path/velocity/angle variance, **click trust
  (`isTrusted`)** and off-centre geometry, keystroke flight/dwell, **input-without-keystroke
  (CDP insertText)**, cold `.value=` writes, scroll, pointer pressure, idle gaps.
- **HONEYPOTS** (`honeypots.js`) — traps disguised as checkout UX:
  - an **off-screen "priority discount" field** (in the a11y tree, invisible to a human) —
    only a DOM/tree-driven agent fills it;
  - an **agentic canary** — an off-screen instruction addressed to "checkout assistants" telling
    them to click an invisible "Apply loyalty discount" button first. A human sees neither; an
    agent reading the DOM to be helpful clicks it. Click = **hard** tell; mere focus = soft;
  - the **order-confirm checkbox** — caught if set via `.checked=true` or an untrusted event;
  - the **slide-to-place-order** control — real drags wobble and vary speed; a straight,
    constant-velocity or dispatched drag is synthetic;
  - **button appear→click latency** (sub-120ms = machine reaction);
  - a **display-only "Pico A1 (Demo)"** product whose detail page says *not for individual
    sale* — buying it is a soft tell that the agent followed instructions literally;
  - **navigation shape** — straight-to-checkout with no browsing.

### Why this won't false-positive like the old one

The old instrument flagged **autofill and fast typing**. Here, signals are split:

- **HARD tells** — things a human physically cannot produce (an `isTrusted=false` event, an
  automation global, a filled invisible field, a cold-set checkbox, a dispatched slide).
  **Any one ⇒ agent.**
- **SOFT tells** — split into **STRONG** (no mouse at all, honeypot kinematics, software GPU)
  and **WEAK** (fast typing, cold `.value=`, timezone mismatch, few fonts). A soft verdict
  needs **two STRONG families, or one STRONG + two WEAK**. **Weak signals alone never flag.**

So browser autofill (cold `.value=` only), a fast typist, a VPN user, and a privacy browser
all stay **human** — each trips at most weak signals. Verified in `scratchpad/test_detector.js`.

## Test protocol (you get one clean run per agent — plan it)

1. **Start fresh:** `rm -f data/store.db && node server.js`. Open `/results` in a tab you keep.
2. **Human control first:** in your own browser, sign in as `rahul_h`, browse a couple of
   phones, add one to cart, check out (check the box, drag the slider). Confirm `/results`
   shows **human** for the checkout row. If not, stop — the baseline is wrong.
3. **Per agent:** give the agent the URL, the account's username/password, and a natural task,
   e.g. *"Go to http://<host>:4600, sign in as `suren_a` / `suren_a@<redacted>`, buy a Pico
   phone, and complete checkout."* Let it run end-to-end.
4. **Mid-session takeover (optional):** sign in yourself, then hand the tab to the agent at the
   product or checkout step. Each sensitive POST is scored independently, so the login row may
   read human while the checkout row reads agent — that transition is the interesting data.
5. **Read `/results`:** every login and checkout is one row — verdict, confidence, tier
   (ENV/BEH/HP/MULTI/SOFT-CORR/OPAQUE), the exact hard/soft tells, order ref, and a ⚠️ if the
   agent bought the display-only demo unit. Full raw bundles are in the `detections` table
   (`bundle_json`) for later analysis.

Notes for a realistic run:
- If the agent **posts the checkout API directly** (no page interaction), it arrives with no
  telemetry → **OPAQUE/agent**. That itself is a strong signal.
- Login is **recorded but not enforced** by default, so agents always reach checkout and you
  capture the whole journey. To gate at login instead, see `ENFORCE_AT_LOGIN` note in
  `server.js`.
- A cloud agent (datacenter browser) will usually trip **ENV** hard (software GPU / webdriver).
  A careful **local** agent in a real browser has a clean environment — it's the **honeypots**
  and CDP-insert tells that catch it.

## Honest limits

- Client signals are spoofable in principle; the server treats them as untrusted and leans on
  hard tells + honeypots that are expensive to fake convincingly. A sufficiently advanced local
  agent that moves a human-like mouse, types with human cadence, avoids the invisible field, and
  drags the slider with real jitter can still pass. The honeypots exist precisely to raise that
  cost; when you find an agent that beats them, the `bundle_json` shows you *how*, which is the
  next iteration's input.
- `webdriver`/automation-global checks catch naive drivers; stealth frameworks hide them, which
  is why the native-function tamper check and the behavioural/honeypot tiers matter more.

## Deploying to AWS (optional)

It's a single zero-dependency Node process serving static files + a SQLite file, so any of:
- an EC2 instance (`node server.js` behind nginx/ALB on your existing domain), or
- a container (one `node:22-alpine` image) on ECS/Fargate.
Put it on your existing test domain over HTTPS (several browser APIs — some fingerprint probes
— only populate on a secure context, so test over `https://`, not plain `http://`, for the
most faithful signals). No secrets, no card processor, no PII store.
